## Claim and finite evidence package

The paper's motivation is one resident filesystem/decoder execution body,
ordinary user execution and independent domain state. It does not require every
workload to beat a specialized library, or every deployment to save memory.

| Question | Existing evidence / gap | Action and completion condition |
| --- | --- | --- |
| Does complex native code serve real applications with private state? | Final optimized correctness, native regression, SIF output, nine identical PFNs already pass | Reuse only with verified unchanged binaries; revalidate changed paths if a candidate is adopted |
| Does XZ optimization improve useful work? | Native fresh sequential −27.06%, application XZ stream −3.43% vs stock; only 1–2 campaigns | Complete the previously registered three-campaign matrix for the frozen version; retain every completed campaign and adverse result |
| Why is Python/XZ still slower? | +16.38% vs stock, shared/copied close; exact decoder contribution missing | Three paired full Python campaigns: stock/library-decoder/common-retained/common-copied/shared, identical original SIF and output oracle, equal loader paths; 120 observations |

No new workload or compression matrix is added. Python is now a fixed separate
task, not a never-consulted held-out test. The complete frozen matrix is 30
campaigns / 7,692 observations; the existing 14 / 4,580 are retained and only
the unstarted 16 / 3,112 are needed if the implementation remains unchanged.
Do not pool a changed frontend or decoder into that version.

Diagnostics precede formal timing. No compilation, profiler, QEMU or competing
task workload overlaps formal measurement. Host CPU/boot settings stay fixed.
Ratios use campaign means of paired log ratios, with campaign-level intervals;
three same-boot campaigns do not establish cross-boot generality or equality.
Never stop because an advantage becomes significant. New candidates need a
separate registration before affected formal measurements.

Main-text priorities: reuse boundary and native changes; actual two-domain
execution; final native cost; copied/shared increment; full application
comparison; maintenance and deployment tradeoffs. Diagnostic histories belong
in the appendix. Include Python and stock-single comparisons even if adverse.
