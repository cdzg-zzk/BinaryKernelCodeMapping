# ISO9660 可行性结论（2026-10-28）

**完整的只读镜像访问可以通过 VKSO 实现，已完成实际共享页执行验证。但当前原型不适合作为 6.5 中“应用收益显著、接入成本低”的主实验。** 它更适合证明适用范围及其代价：复杂的文件系统读取逻辑能够复用，但需要明确的服务边界，并不等于直接复用整个文件系统。

这不是根据未适配驱动的静态检查失败作出的否定。此次实现并运行了真正的内核文件系统消费者、用户态消费者、同布局复制对照和独立库对照。尚未开展原生机器上的 VKSO 性能测量，也没有运行 LKL/rump 性能对照；因此没有“比 LKL 更快、更省内存”的实验结论。

## 实际完成的任务和证据

原始实现来自本机 Linux 5.15.198 的 `fs/isofs`，字符转换来自同一源码的 `fs/nls/nls_base.c`。为使用已有隔离测试环境，原始参考与适配模块均按 Ubuntu `5.15.0-119-generic` 的 ABI 编译。源码版本和运行内核版本不能混为一谈。

测试任务包括打开 ISO 镜像、逐层路径查找、目录遍历、元数据、符号链接、完整文件读取、非对齐跨块读取、随机偏移读取、EOF 和不存在路径。没有将单个 extent/名称转换函数当成完整文件系统实验。

| 输入 | 模式 | 目录项数 |
|---|---|---:|
| 官方 Alpine `alpine-virt-3.20.10-x86_64.iso`，63,963,136 字节 | 默认 | 126 |
| Joliet 镜像，含中英文/希腊文名称 | 默认 | 13 |
| Rock Ridge + Joliet 混合镜像 | 默认 | 20 |
| 同一混合镜像 | `norock` | 19 |
| 非连续 multi-extent 文件镜像 | 默认 | 2 |
| Rock Ridge 镜像，含长名称、长链接、深目录 | 默认 | 20 |

合计 200 个目录项、145 个普通文件。每次完整用户测试另执行 870 次偏移读取、145 次 EOF 读取和 57 次不存在路径查询。真实 Alpine 镜像包含的普通文件内容共 63,299,099 字节；镜像 SHA-256 已与发行方公布值核对。

最终运行：[`export-03/evidence/result.json`](../evaluation-local/runs/iso9660/export-03/evidence/result.json)。

| 检验 | 实测结果 |
|---|---|
| 适配后的真实内核挂载读取 | 六组与原始驱动完全一致 |
| VKSO 用户态读取 | 六组路径、元数据、链接目标、文件哈希完全一致 |
| 复制活动 carrier 字节得到的相同布局普通 DSO | 六组完全一致；五个页均不与内核共享 PFN |
| 两个并发 VKSO 用户进程 | 均通过六组测试；五个代码/常量页均与内核共享 PFN |
| 并发进程的依赖表 | 同时驻留时 PFN 不同，证明表为进程私有 |
| 共享注册仍有效时再次执行内核挂载读取 | 六组完全一致 |
| 解除注册、重新检查页、卸载消费者与 owner | 全部通过 |

所有特权实验都在私有 QEMU TCG 客体内进行。没有把 TCG 耗时用作性能结果。用户态复制实现也在宿主机运行通过，但 Python 校验器的耗时不是正式应用吞吐数据。

## 为什么这个版本符合 VKSO 条件

复用边界是镜像解析、目录/名称/Rock Ridge/Joliet 处理、inode 信息解析及块映射。内核路径继续使用真实 VFS 和块缓存，用户路径使用进程自己的对象和 `pread`。

1. **指令及寻址。** 公共对象采用相对寻址，关闭该对象上的 fentry、栈保护和不适用的插桩，并处理内核/用户调用栈对齐。最终 `iso_read_super` 静态检查通过；函数指针目标还通过绑定表审计及执行覆盖核验。静态 PASS 不等于证明所有间接控制流都正确。
2. **依赖闭包。** 保留 29 项显式服务绑定。内核绑定到原生分配、buffer head、inode、dentry 等操作；用户绑定到私有对象、内存分配和字节 I/O。没有将用户调用转发到内核函数地址。
3. **状态所有权。** 用户 image handle 内含私有 superblock、inode 缓存和临时 buffer head；不会访问真实挂载的内核 inode/dentry/cache。ISO 只读不代表这些执行状态不发生变化。
4. **真实驻留消费者。** `vkso_iso_core.ko` 持有公共实现；`vkso_isofs.ko` 是实际可挂载并读取这些镜像的文件系统。共享页来自这个被内核使用的 owner，不是为了用户态实验加载的一组闲置算法函数。
5. **物理复用。** 实际注册四个代码页和一个只读数据页，共 20 KiB。共享用户映射、复制对照映射以及解除注册后的映射均检查了 PFN。

适用范围是所测的只读镜像 API，而非任意 POSIX 文件系统或整个 Linux isofs 子系统。用户桥采用 UTF-8；没有实现用户态 zisofs 解压、设备操作、通用 VFS、跨线程共享同一 handle、缓存回收策略和完整挂载选项。遇到压缩文件内容读取会返回不支持，不能声称支持了全部 isofs 功能。多个独立 handle/process 的状态是独立的。

## 成本核算与 6.5 判断

源代码明细见 [`costs-01.json`](../evaluation-local/runs/iso9660/costs-01.json)。计数包含空行和注释，机械移位与实质修改分别记录：

- 从 isofs 移出 28 个函数，原函数合计 2,092 行；四个函数发生主体边界修改。排除去除 `static` 后，函数体比较为增加 13 行、移除 73 行；其中部分逻辑转入内核 wrapper，不能把移除行数解释为删除了相应功能。
- 另复用三个 NLS 辅助函数及其表，合计 122 行；增加绑定表初始化/地址访问入口。
- 用户桥为 251 行。内核支持、owner 元数据、类型声明、重映射及用户绑定等生成文件另有 293 行；原 inode/链接函数中的 wrapper 也属于适配范围。生成和用户构建脚本合计 386 行。上述各项不能只挑一个最小数字作为“接入成本”。
- 未修改通用 carrier builder 或注册模块来让本例通过；但确实调整了源码组织、内核消费者和编译选项，并引入了明确的用户态服务实现。

最终客体内的实际模块占用（`/proc/modules`），以及活动管理进程占用：

| 项目 | 观测值 | 解释 |
|---|---:|---|
| 可消除的重复代码/只读页 | 20 KiB | 同一布局的复制对照实际多占的五个物理页；不是整套服务的净节省 |
| 原始 isofs 模块 | 48 KiB | 同源、同 ABI 的完整参考模块 |
| 适配后的 core + 文件系统消费者 | 36 + 36 = 72 KiB | 当前组织方式比原模块增加 24 KiB |
| VKSO 注册模块 | 36 KiB | 部署成本；若已有多个导出可另报摊销成本 |
| 当前活动 manager | RSS 1,684 KiB；PSS 1,681 KiB | 当前静态链接管理程序的客体实测值，不是机制的不可优化下限 |
| PFN 观测辅助模块 | 16 KiB | 测试工具，排除在部署成本之外 |

因此必须分两种口径：

- **已有适配内核与通用注册服务时的增量口径：** 本案例可以证明五个页的物理合并。普通 DSO 本来也会在用户进程间共享代码，不能把收益写成“20 KiB × 进程数”。
- **为 ISO 任务首次部署的完整口径：** 当前新增内核模块占用已大于这 20 KiB，还要加注册与管理服务。现有证据不能支持整体内存更省。

拆分模块、页对齐和管理程序都能继续优化，上述结果不是 VKSO 的理论下限，也不是“文件系统不适用”的证明。但优化这些成本本身是额外工作，尚不能当作已取得的收益。ISO 驱动在目标机器上是否自然驻留、是否存在实际内核消费者，也必须单独证明，实验中主动加载不能替代部署动机。

**决策：保留本原型作为完整任务的可行性和边界证据，暂不将其扩展为 6.5 的主要应用收益实验。** 如果 6.5 要回答“能否复用比算法更复杂的真实内核实现”，本例有价值；如果要回答“为什么实际应用值得采用 VKSO”，目前不足。现在没有理由为了制造相对 LKL 的漂亮数字而忽略普通库及上述成本。

## 合适的外部对象与公平比较边界

| 对象 | 为什么相关 | 本次证据与后续公平边界 |
|---|---|---|
| LKL `fs2tar` / `cpfromfs` | 直接读取文件系统镜像，是它真实、合理的用途 | 官方工具与接口已核验；未构建/计时。应配置 ISO9660 及所需扩展，用相同镜像完成同一转换或提取任务，合理裁剪无关子系统。LKL 是原生库化内核，不是指令模拟器 |
| rump 的 cd9660 + fs-utils | 使用 NetBSD 文件系统实现完成用户态镜像访问 | 任务匹配，但实现和内核版本不同，应作为系统级方案比较。`rump_cd9660` 手册中的挂载前端是 PUFFS/p2k，不能直接称为 Linux FUSE |
| libarchive | 已有实际应用使用的独立用户态 ISO 实现 | 已运行 3.6.0。真实 Alpine 与 Joliet 镜像的完整路径/内容一致。适合作为普通库对照；接口偏流式遍历，随机路径任务须计入相应索引代价 |
| GNU libiso9660 / `iso-read` | 普通用户态 ISO 库及现成读取工具 | 137 个文件比较中 129 个一致；七个路径读取失败、一个多段文件内容不一致。当前结果只说明所测 CLI 组合的行为，不能概括为库不支持相应扩展 |
| FuseISO / `lklfuse` | 面向现有应用提供挂载文件系统 | 只有任务需要挂载接口时才是对应的应用方案。若比较复用机制，应使用相同前端/请求语义，不能把直接库调用与 FUSE IPC 的差异全部归功于 VKSO |
| Bento（FAST 2021） | 同一文件系统跨内核/用户执行及调试，概念上接近 | 应在相关工作中深入比较；它采用 Rust 文件系统及不同部署目标，不是可直接替换的 ISO 实现，不能强行作为同格式性能基线 |

独立实现的差异没有隐藏：libarchive 的 multi-extent 两个文件字节和大小均与 Linux 一致，路径差异来自保留大写名称；不能称其“多段读取错误”。Rock Ridge 的 `rr_moved` 可见性、长链接目标及 `norock` 深目录还存在差异，保留在原始结果中。若继续测性能，首先使用已确认共同语义的真实 Alpine 镜像，扩展覆盖另列兼容性表。

适合进一步做的真实任务是“发行版镜像检查/提取或转换为归档”，可对接现成 `fs2tar` 工作流；不是只测 `lookup` 或某个解析循环。只有在确认这个任务能体现明确的复用收益后，才值得投入 LKL/rump 的版本固定、裁剪和原生性能对照。本次没有将尚未完成的外部性能比较写成结果。
