# VKSO 开发工作量与代码规模评估

日期：2026-07-28
对象：Linux 5.15.198 x86-64 Raw vDSO 与 VKSO ABI 10
VKSO 实现提交锚点：`be35a28d`；最终实验包提交：`66e7b1e`
Raw 源码锚点：Linux stable v5.15.198；官方 tarball SHA256
`5d4c0994580dd3bbd5ffc5fcb81c22dd305b844c9d8c7b176cc41b28f7e29743`

## 1. 最终结论

本报告使用人工语义清单决定归属，脚本只负责对选定范围求和。最终功能配置启用
`CONFIG_VKSO_TIME`和`CONFIG_TIME_NS`，因此下列内容不计入功能工作量：

- 64 SLOC编译期`static_assert`和专用include；
- Raw 14 SLOC、VKSO 59 SLOC的`CONFIG=n`兼容桩；
- benchmark、probe、QEMU/裸机脚本和报告。

此外，`timekeeper → vkso_shared_data`转换是为了在当前原型中保留既有
`struct timekeeper`和其他内核reader，现已物理隔离到
`kernel/time/vkso_time_compat.h`，共60 SLOC，并作为兼容适配单独披露。

本次重新审计纠正了旧清单的一个遗漏：旧表没有计入
`posix-timers.c`中必需的`vkso_current_mm_data()`。当前表已经逐项纳入
MM_data选择、共享core调用和fallback，因此不能再沿用旧报告中的
1,038/1,098 SLOC。

| 设计功能切片 | Raw | VKSO | VKSO - Raw |
|---|---:|---:|---:|
| 主运行时功能 | 1,076 | 1,042 | -34 |
| Raw syscall直接依赖的共享reader | +125 | — |  |
| **内在功能合计** | **1,201** | **1,042** | **-159（-13.24%）** |
| VKSO timekeeper兼容适配 | — | +60 |  |
| **当前原型实际合计** | **1,201** | **1,102** | **-99（-8.24%）** |

VKSO为其他内核调用者和unsupported-clock fallback保留的旧`ktime_get_*`
没有计入VKSO功能切片；Raw侧125 SLOC被计入，是因为Raw目标syscall确实直接
依赖它们。

core复用收益可以完整对账：

| 对账项 | Raw | VKSO内在功能 | 差异 |
|---|---:|---:|---:|
| user reader + kernel reader / shared reader + wrapper | 593 + 125 = 718 | 467 + 126 = 593 | -125 |
| 发布、映射、namespace、ABI、PV/HV等机制 | 420 | 351 | -69 |
| syscall边界（含MM_data选择） | 63 | 98 | +35 |
| **合计** | **1,201** | **1,042** | **-159** |

把60 SLOC timekeeper兼容适配加回后，VKSO机制侧为411 SLOC，仍比Raw少9
SLOC；当前原型总量仍减少99 SLOC。reader维护切片恰好减少125 SLOC
（-17.41%），等于Raw目标syscall直接依赖的第二份kernel reader规模。这里说的是
目标功能的维护归属，不是声称完整内核已经物理删除旧reader。

按纠正后的同一范围，优化前`9ad92a1`为1,062 SLOC内在功能、1,122 SLOC当前
原型；当前`be35a28`分别为1,042和1,102 SLOC，减少20 SLOC。具体是reader
469+129降为467+126（-5），syscall/MM_data选择从113降为98（-15），机制部分
保持351；不是通过漏算路径取得的减少。

较早的源码去重没有用通用运行时分派换取行数：五个高精度和两个coarse reader
由宏生成专用函数，用户wrapper仍直接tail-jump。当前紧凑提交进一步改变了参数
ABI、MM_data选择和fallback机器码，因此“与`9ad92a1`机器码相同”只适用于历史
去重提交，不适用于当前`be35a28`；当前二进制已重新测量。

最终机器码同样支持复用结论：Raw目标vDSO entry加目标kernel reader为2,497 B；
VKSO shared core加生产wrapper为2,401 B，减少96 B（-3.84%）。

## 2. 比较边界

### 2.1 纳入

- `clock_gettime`七个直接支持clock及CPU/alarm/无效ID fallback；
- `clock_getres`、`gettimeofday`、`time`、`getcpu`完整语义；
- TSC、time namespace和源码能力中的PVClock/Hyper-V冷路径；
- shared/VVAR数据、seq、映射、每MM context、生命周期和ABI接入；
- Raw目标syscall实际调用的125 SLOC共享kernel reader。

### 2.2 排除或单列

- IA32、x32、32位time ABI、legacy vsyscall、SGX entry；
- 通用timekeeper/NTP生产者以及通用MM/ELF/syscall基础设施；
- 两边未实质重写的`vdso/clocksource.h`、`vdso/ktime.h`和
  `vdso/math64.h`；
- 编译期验证和最终配置不进入二进制的stub；
- timekeeper到VKSO的60 SLOC兼容适配；
- 构建工具、通用项目基础设施和测试。

### 2.3 构建工具

Raw使用内核内置vDSO linker/image链；VKSO使用项目级`make_dll`和页面替换
机制。二者复用边界不同，因此运行时功能、构建胶水、通用机制适配和既有基础设施
必须分表，不能随意相加。

## 3. 旧“491行”为什么不成立

491只是`syscall 63 + 旧reader 125 + 发布74 + 主映射229`。它一方面混入了
整个内核共享的reader，另一方面漏掉time namespace、auxv/mm_context、VVAR
架构接口、PV/HV和配置接入。

按最终配置，Raw kernel专属运行时支持约483 SLOC：

`syscall 63 + 发布80 + 映射229 + timens 66 + 配置/ABI 31 + 虚拟化14`。

另有125 SLOC reader是Raw目标syscall的可归属依赖，但不是vDSO专属代码。

## 5. user/kernel归属

VKSO core位于kernel tree，但同时由kernel和user执行，不能只按文件路径归类：

| 系统 | user专属 | kernel/user共享 | kernel专属 |
|---|---:|---:|---:|
| Raw | user vDSO 593 | 无共享reader | 483；另有125 SLOC可归属reader |
| VKSO内在功能 | wrapper 126 | shared core 467 | 449 |
| VKSO兼容适配 | — | — | 60 |

因此用户专属源码从593降至126 SLOC，减少467 SLOC（-78.75%）；这467 SLOC
不是消失，而是成为kernel/user共享core。把Raw第二份125 SLOC kernel reader也
纳入后，reader维护切片从718降至593 SLOC，减少125 SLOC（-17.41%）。

内在kernel专属机制从483降至449 SLOC，减少34；加入当前原型的60 SLOC
timekeeper适配后为509，比Raw多26 SLOC。也就是说：

- 用户侧重复实现确实大幅缩小；
- 总体仍减少99 SLOC；
- 当前kernel专属部分略增，原因是兼容现有timekeeper的转换层，而不是共享core
  又复制了一份算法。

完整内核中保留的旧reader仍服务其他调用者和unsupported-clock fallback，所以
这是目标功能的语义归属收益，不宣称旧reader已从整个kernel tree物理删除。

### 5.1 VKSO中保留但不计入最终功能的源码

| 类型 | 有效SLOC | 是否VKSO新增 | 主表处理 |
|---|---:|---|---|
| `CONFIG_VKSO_TIME=n`接口桩 | 50 | 是 | 最终配置不编译，单列 |
| `CONFIG_TIME_NS=n`签名兼容桩 | 9 | 仅部分签名调整 | 最终配置不编译，单列 |
| 原有`ktime_get_*`及直接helper切片 | 125 | 否 | 其他reader/fallback仍需要，不算VKSO新增 |
| 原有timekeeper生产状态切片 | 40 | 否 | 其他reader/NTP仍需要，不算VKSO新增 |
| timekeeper到shared_data适配 | 60 | 是 | 当前实际原型计入，内在设计单列 |
| 编译期ABI断言 | 64 | 是 | 验证代码，不生成运行指令 |
| 功能、read、update测试 | 2,521 | 是 | 研究验证工作，不计产品功能 |

这里最关键的区别是“物理存在”和“目标功能工作量”：

- 125 SLOC旧reader和40 SLOC timekeeper状态在VKSO源码树中仍然存在，但不是
  VKSO为了目标功能新增的代码，也不应伪装成已经删除；
- 60 SLOC转换层确实是当前原型为兼容既有timekeeper新增的成本，所以在
  1,102 SLOC当前原型总数中计入；
- 59 SLOC关闭配置桩和64 SLOC断言属于可维护源码，但不进入最终实验运行路径，
  因此不能混入reader性能对应的功能规模。

## 6. 构建与通用机制

### 6.1 功能构建胶水

| 系统 | 有效 SLOC | 内容 |
|---|---:|---|
| Raw | 158 | x86-64 vDSO Makefile、version/layout linker、VVAR linker/Kbuild |
| VKSO | 48 | Kconfig、Kbuild 与 shared text/data linker section |
| VKSO private-wrapper 适配 | 210 | ET_REL wrapper 重定位、导出和 CLI；单列 |

若把本实验为 wrapper 新增的通用 builder 能力也计入本次开发工作，VKSO 构建侧
为 258 SLOC，比 Raw 的 158 多 100。它没有进入运行时主表。

### 6.2 既有可复用基础设施

- Raw 依赖既有 `vdso2c.c/.h` 和 generic vDSO Makefile；人工清单中为 336
  有效 SLOC，但它同时处理 32/64 位，不能当作本实验五类接口算法。
- VKSO 的通用 `make_dll`、page-cache replacement 和 manager 早已存在，不能
  全部归给 time。
- time 实验前的 `shared_data` R--/NX 支持提交在三个语义相关文件中为
  **新增 255、删除 13 个 Git 行**：builder +238/-11、manager +2/-1、
  CLI +15/-1。
- 本次 private-wrapper 通用适配为 **Git +227/-1**；其最终人工语义范围为
  210 有效 SLOC。

因此论文应把“time 功能源码”和“项目通用机制复用/扩展”分表，不能把后者隐藏，
也不能把整个多年积累的项目基础设施都算成这次 time 开发。

## 7. no-vDSO 到 VKSO 的开发增量

对 `5b7386b` no-vDSO 基线到最终 VKSO 的人工增量清单：

| 类型 | 物理行 | 有效 SLOC |
|---|---:|---:|
| time/getcpu 内在生产功能增量 | 1,288 | 1,039 |
| timekeeper兼容适配 | 82 | 60 |
| private-wrapper 构建适配 | 226 | 210 |
| 测试与 benchmark | 2,828 | 2,521 |

1,039与前面的最终运行时1,042不矛盾：

- 1,039回答“从no-vDSO基线实际新增/实质改写了多少”，包含build glue，
  syscall 只计改写部分；
- 1,042回答“最终相同语义边界需要维护多少运行时源码”，包含完整syscall
  边界，不包含 build glue。
- 60 SLOC timekeeper转换在两种视图中都单列，不混入内在功能。

另外，VKSO自身三个新接口头中的50 SLOC `CONFIG_VKSO_TIME=n`桩是兼容性开发
成本，但不进入最终配置；它们已在5.1节披露，不塞入1,039 SLOC生产功能数。
如果论文讨论“所有开发和验证投入”，应将产品、兼容适配、通用builder扩展、
关闭配置维护和测试五项分列，不能合成一个看似精确但语义混乱的总行数。

no-vDSO 完整源码树没有被完整纳入 Git，只保存了关键文件基线，因此当前不能
严谨声称一个对称的 “no-vDSO→Raw Git 新增/删除总数”。Raw 侧应使用本报告的
最终语义清单；若论文必须给出对称 Git churn，需要先从官方 v5.15.198 重新生成
并提交完整 no-vDSO 基线，再分别应用 Raw/VKSO 补丁。

## 8. 二进制规模

| 指标 | Raw | VKSO | 差异 |
|---|---:|---:|---:|
| 目标 user entry/functions | 1,515 B | wrapper 238 B | -1,277 B（-84.29%） |
| 目标 kernel/shared reader | 982 B | shared core 2,163 B | 不宜孤立比较 |
| **reader 合计** | **2,497 B** | **2,401 B** | **-96 B（-3.84%）** |
| 发布函数 | 575 B | 459 B | -116 B（-20.17%） |
| 最终 `bzImage` | 8,422,400 B | 8,419,264 B | -3,136 B（-0.0372%） |
| 全局共享时间 payload | 480 B | 184 B | -296 B |
| per-MM payload | timens 时另页 | 40 B payload / 4 KiB 页 | 语义不同，不直接相减 |

`libkernel.so` 文件为 23,288 B，但包含页对齐占位、动态元数据、共享内核页和
private wrapper 页，不能把文件大小当作新增函数机器码。当前两侧`.text`都因链接
对齐为14,683,442 B；选定file-backed section之和反而是VKSO多3,072 B，而压缩
`bzImage`是VKSO少3,136 B。这两个方向不同并不矛盾：section对齐、`.data`布局
和压缩率会淹没几KB以内的目标函数差异，因此论文的核心代码规模证据应使用逐
symbol合计，整镜像只作为补充。

当前VKSO symbol由最终normal配置、GCC 11.4对象重建取得；wrapper直接取最终
`libkernel.so`符号。`vkso_read_cycles_cold`在DSO占位页中的symbol size会被
builder扩展到页尾，不能使用该值，因此采用原始对象中的111 B真实函数尺寸。

## 9. 论文可使用的表述

推荐：

> 在相同x86-64 time/getcpu功能边界和最终配置下，Raw目标功能为1,201 SLOC；
> VKSO内在功能为1,042 SLOC，减少159 SLOC（-13.24%）。当前原型为兼容既有
> timekeeper另需60 SLOC适配，计入后仍为1,102 SLOC，减少99 SLOC
> （-8.24%）。用户专属源码从593降至126 SLOC；把共享core纳入后，reader维护
> 切片从718降至593 SLOC（-17.41%），对应机器码从2,497 B降至2,401 B
> （-3.84%）。

不推荐：

- “Raw kernel 只有 491 行”；
- 只说“VKSO user只有126行”却不披露467 SLOC shared core；
- “旧 `ktime_get_*` 已从完整内核删除”；
- 把测试、整个 `make_dll` 或整个 `vdso2c` 混入一个总数；
- 只报告物理行或只报告有效 SLOC，而不解释二者方向不同。
