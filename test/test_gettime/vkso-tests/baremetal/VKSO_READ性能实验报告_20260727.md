# VKSO Reader 四镜像性能实验报告

> 实验批次：`20260727T124135Z-vkso-final`  
> 实验平台：Intel NUC 裸机，Linux 5.15.198  
> 对比对象：原生 vDSO（raw）与 VKSO  
> 文档范围：用户态 reader、直接 syscall、seq 读取协议；不包含 update-side 性能

## 1. 实验目的与结论

本实验回答以下问题：

1. VKSO 是否完整复现了本实验覆盖的原生 vDSO time/getcpu 语义；
2. VKSO 用户态 reader 与原生 vDSO 相比快慢多少；
3. 性能差距来自 return thunk/retpoline，还是来自 VKSO 自身的入口、上下文和核心算法组织；
4. VKSO 是否改变了直接 syscall 的性能；
5. VKSO 的 seq 重试协议是否有效。

本轮四个镜像、四个用例均完整收集，功能矩阵全部通过。核心结论如下：

- 在默认内核配置下，20 个用户入口的几何平均结果为 **VKSO 比 raw vDSO 慢 2.37%**；其中 17 个用户态快路径慢 **2.30%**，3 个 fallback 路径慢 **2.74%**。
- 绝对差距很小：17 个用户态快路径的中位绝对差值只有 **约 0.30 cycles**。很多只有 15–22 cycles 的短接口中，额外 1 cycle 会表现为 5%–10% 的相对差异。
- 关闭本实验定义的 thunk/retpoline 相关配置后，20 个用户入口仍慢 **2.09%**。相对默认配置只缩小约 **0.28 个百分点**，说明 thunk 不是主要瓶颈。
- VKSO 的典型快路径比 raw 多退休约 **4 条指令、3–4 个分支**。主要额外成本来自入口 wrapper、显式 context/MM_data 依赖、clock 分类和独立 core 函数边界。
- VKSO seq 重试率显著下降：高精度协议减少 **92.5%–94.8%**，RAW 协议减少 **96.1%–96.7%**。但冲突本来就极少，降低重试只能节省极小的平均成本，无法抵消每次读取固定增加的约 1 cycle。
- 默认配置下，VKSO 镜像中的直接 syscall 几何平均比 raw 镜像快 **1.70%**；no-ret 配置下快 **0.84%**。这是同一轮实验的观测结果，但差距可能包含跨启动、代码布局和内核构建差异，不能仅凭一次四镜像实验归因为 VKSO 架构收益。
- 就 reader 而言，当前 VKSO 已经接近 raw vDSO，但尚未整体超越 raw。继续优化应优先消除固定入口和根 namespace 的上下文成本，而不是继续追逐 seq 重试或 cache miss。

## 3. 测量内容



### 3.1 20 个接口场景

测试程序覆盖以下 20 个场景：


| 类别                         | 场景                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------- |
| `clock_gettime` 高精度快路径     | `CLOCK_REALTIME`、`CLOCK_MONOTONIC`、`CLOCK_MONOTONIC_RAW`、`CLOCK_BOOTTIME`、`CLOCK_TAI` |
| `clock_gettime` coarse 快路径 | `CLOCK_REALTIME_COARSE`、`CLOCK_MONOTONIC_COARSE`                                      |
| `clock_gettime` fallback   | `CLOCK_PROCESS_CPUTIME_ID`、`CLOCK_REALTIME_ALARM`                                     |
| `clock_getres`             | realtime、realtime coarse、process CPU fallback                                         |
| `gettimeofday`             | 仅 timeval、仅 timezone、两者均非 NULL、两者均为 NULL                                              |
| `time`                     | `time(NULL)`、`time(&value)`                                                           |
| `getcpu`                   | CPU/node 均输出、两个输出均为 NULL                                                              |


每个场景测量两条调用路径：

- `syscall`：测试程序直接执行相应系统调用；
- `user`：raw 镜像调用原生 vDSO，VKSO 镜像调用 `libkernel.so` 中的 VKSO wrapper。

本轮 `INCLUDE_CORE=0`，因此没有把仅供开发诊断的裸 `core` 入口当成正式 ABI 路径。比较的是应用实际应使用的完整 user entry。

性能表的 20 个场景不是全部功能覆盖。76 项功能矩阵还额外验证了：

- `CLOCK_THREAD_CPUTIME_ID`、`CLOCK_BOOTTIME_ALARM` 和无效 clock ID 的 fallback；
- `clock_gettime`/`clock_getres` 的 NULL 与非法地址语义；
- `getcpu` 的 CPU-only、node-only、cache 参数、NULL 和多 CPU/多线程组合；
- time namespace 的五类快路径 offset；
- namespace 的 `exec`、`setns` 和生命周期行为。

因此，性能表负责回答热点延迟，功能矩阵负责证明更宽的 ABI/路径语义，两者不能互相替代。

### 3.2 计数器

每个样本同时收集：

- TSC wall-clock cycles；
- PMU cycles；
- retired instructions；
- branches 和 branch misses；
- cache references 和 cache misses；
- L1D load misses；
- LLC load misses。

主表使用每个接口 31 次重复的 **中位数**。总览中的百分比使用各接口“VKSO 中位数 / raw 中位数”的几何平均，避免长 syscall 对短接口的算术平均造成权重失衡。

### 3.3 seq 协议

seq 测试分别执行：

- 高精度共享时间数据读取协议；
- `CLOCK_MONOTONIC_RAW` 共享数据读取协议。

每项执行 `100,000,000` 次，记录平均 cycles 和 retry 次数。

## 4. 实验控制条件

关键参数来自本轮 manifest：

```text
benchmark_cpu=2
housekeeping_cpus=0-1,3
iterations=500000
repeats=31

include_core=0

```

四次启动均满足：

- benchmark 固定在 CPU 2；
- CPU 2 通过内核参数隔离；
- governor 为 `performance`；
- min/max performance 均为 100%；
- turbo 关闭；
- TSC 可用；
- `nosmt` 生效，`lscpu` 显示每核 1 线程；
- 除所选 Image 外，raw/VKSO 同一变体的启动参数保持一致。

日志中四组都会出现 `idle=poll and HT enabled` 警告，但四组对称出现，而且系统运行时每核仅 1 线程，因此它不是 raw/VKSO 差异来源。

## 10. 为什么 VKSO reader 仍略慢



### 10.1 benchmark 调用方式没有额外偏向 raw

raw vDSO 入口通过 `AT_SYSINFO_EHDR` 解析后，以函数指针调用；VKSO 入口由测试程序直接链接 `libkernel.so` 中的 `__vkso_*` wrapper。也就是说，本轮调用点并没有让 VKSO 多做一次动态符号查找，反而省去了 raw 的函数指针间接调用。

因此剩余差距来自 VKSO 入口和 core 内部，而不是 benchmark 用了“不常用的 VKSO 调用方式”。

### 10.2 VKSO wrapper 仍需建立显式依赖

VKSO 的目标是把可复用内核 core code 导出给用户态。core 不再隐式依赖传统 vVAR 固定布局，而是显式接收：

- shared time data；
- per-MM `MM_data`；
- cycles context；
- fallback context/mode。

当前 assembly entry 已经使用 RIP-relative 地址并以 tail jump 进入专用 core，没有 PLT/GOT 往返；但构造这些参数仍会产生 `LEA`、load、clock ID 比较和分支。对于 15–60 cycles 的接口，这些固定工作就是主要差距。

### 10.3 user root time namespace 仍支付 MM_data 检查

这里需要区分 kernel reader 和 user reader。

- kernel reader 已经在 `vkso_current_mm_data()` 中识别初始 time namespace，并为根 namespace 传入 NULL；
- user wrapper 必须始终保存真实的 per-MM `MM_data` 地址，因为同一进程可在 wrapper 初始化后通过 `setns()`/fork 生命周期进入带 offset 的 time namespace，内核会原地更新该页的 `clock_mask` 和 offset。

因此，user reader 在 monotonic、raw、boottime 和 monotonic coarse 路径确实要读取 `clock_mask`。不能在初始化时看到 mask 为零就永久绑定 NULL，否则运行中的 `setns()` 会继续走根 namespace 路径，破坏语义。

原生 vDSO 的做法依赖特殊的 per-MM vVAR 映射：time namespace 页把 seq 保持为奇数并设置特殊 clock mode，普通根 namespace 只有在本来就进入 odd-seq 冷分支时才检查 namespace。VKSO 若完全照搬，需要重新引入一个把 per-MM sentinel 和全局 shared payload 组合起来的 vVAR 类映射，或者建立可被 setns 动态更新的入口选择机制；这会明显扩大映射、生命周期和 ABI 复杂度，不是当前首选优化。

可以安全做的小优化是统一内部 ABI：所有调用者都传入非 NULL 的 `MM_data`，kernel 根 namespace 使用一个只读零 mask 对象，user 继续使用真实 per-MM 页。这样可以删除 core 中的 `mm_data &&` 检查，但仍保留一次必要的 `clock_mask` load。它预计只能节省一个已预测分支，收益较小但语义清楚、代码也会减少。

### 10.4 “other clock” 分类带来更多固定工作

VKSO 为保持结构清晰，把 realtime、monotonic、coarse 和 other clocks 分为不同 core。`RAW/BOOTTIME/TAI` 进入 other 路径后，还要选择 base、决定 namespace offset 并执行对应换算。

PMU 数据与此一致：

- monotonic raw：约多 22 条指令、5 个分支；
- boottime：约多 30 条指令、9 个分支；
- TAI：约多 25 条指令、8 个分支。

原生 vDSO 的通用实现大量 inline，编译器可以跨 clock dispatch、数据读取和结果归一化做整体优化。VKSO 的 `noinline` 专用 core 和导出边界降低了这种跨函数优化空间。

### 10.5 fallback 的相对额外成本

原生 vDSO **同样不是一开始就直接 syscall**。它先进入 `__cvdso_clock_gettime_common()`/`__cvdso_clock_getres_common()`，判断 clock ID 和支持位图；返回失败后，再由外层 `*_fallback()` 发起 syscall。因此不能把 VKSO 的全部 dispatch 都算作相对 raw 的额外成本。

VKSO 真正多出的部分是：

- user entry 和 shared `other/core` 之间更深的函数组织；
- shared core 为同时服务 kernel/user 而执行的 `context->fallback_mode` 选择；
- out-of-line `vkso_fallback()` 的参数准备和调用/返回。

用同一镜像的“完整 user fallback 减直接 syscall”消除大部分 syscall 主体后，normal 组中 VKSO 相对 raw 的增量为：

| fallback 场景 | 额外 cycles | 额外指令 | 额外分支 |
|---|---:|---:|---:|
| clock_gettime process CPU | +17.53 | +29 | +9 |
| clock_gettime realtime alarm | +17.23 | +29 | +9 |
| clock_getres process CPU | +14.47 | +15 | +7 |

因此 fallback 差距真实存在，但原因应表述为“VKSO 比 raw 多一层环境选择和函数边界”，而不是“raw 没有前置 dispatch”。优化时也不应为了这些冷路径给所有快路径增加一次返回检查。

### 10.6 极短接口中的百分比放大

例如 `time`、`clock_getres`、`getcpu` 和 NULL 参数路径只有约 15–25 cycles。此时：

- 1 cycle / 17 cycles = 5.9%；
- 2 cycles / 18 cycles = 11.1%；
- 3 cycles / 22 cycles = 13.6%。

因此 `getcpu both +13.63%` 并不表示多执行了一个复杂算法，只是 no-ret 组中相差约 3 cycles。normal/no-ret 之间若代码布局和对齐稍有变化，结果就可能改变正负号。评价这类接口时必须同时报告 cycles 和百分比。

### 10.7 return thunk 不是主因

关闭诊断组中的 thunk/retpoline 相关配置后：

- 全部 user 入口由慢 2.368% 变为慢 2.093%；
- 只改善约 0.275 个百分点；
- retired instructions 和 branches 的 VKSO/raw 差值基本不变。

因此 return thunk 可以贡献少量 cycles，但无法解释主要差距。若继续优化，应先处理 wrapper/context/dispatch，而不是通过改变安全编译选项追求结果。

### 10.8 retry 优势与 reader 固定成本相互独立

retry 优势和 reader 固定成本是两个独立因素，并不是 VKSO 为了降低 retry 而在 reader 上增加了固定指令。

- VKSO writer 先在私有 snapshot 中完成派生计算，只在 odd seq 区间复制最终字段，所以 reader 可见的 odd 窗口较短；
- reader 仍使用标准的两次 seq 观察、内存顺序约束和失败重试；
- 把派生计算重新移入 odd 区间只会增加重试，不会减少 reader 的任何 load、compare 或 branch。

seq observer 中 VKSO 约多 1 cycle，也不能直接解释为生产 reader 的“seq 固定税”：raw/VKSO observer 访问的结构布局和测试函数并不完全相同。生产性能应以完整接口及 PMU 数据为准。

对完整 reader 延迟而言仍可使用以下模型：

```text
平均成本 = 无冲突固定成本 + retry 概率 × 单次 retry 成本
```

当前 retry 概率太低，所以降低 retry 对平均 reader 延迟的贡献很小；但这不意味着应主动放弃该优势。seq 本身用于防止跨更新时间点读取到撕裂的 base/cycle 参数，不能删除。正确方向是保留较短的 writer odd 窗口，同时独立减少入口、dispatch 和 namespace 检查的固定成本。

## 11. 当前实现中已经有效的优化

本轮结果也证明了若干设计并非纯粹负担：

- `CLOCK_REALTIME` 专用入口在两种编译配置下都比 raw 快约 1%–2%；
- `CLOCK_MONOTONIC` 也稳定略快；
- `gettimeofday timeval` 在 normal 下基本持平；
- `time(NULL)` 在两个变体下均不慢；
- VKSO seq retry 显著低于 raw；
- 直接 syscall 没有出现系统性退化。

这说明 shared data 设计和导出 core code 本身可以形成高效快路径。问题集中在某些入口仍携带通用上下文成本，而不是 VKSO 架构必然比 vDSO 慢。

## 12. 建议的后续优化顺序

重新对照源码、PMU 和 `setns()` 生命周期后，建议按以下顺序做小步 A/B 实验。

1. **建立非 NULL MM_data 内部约束**：kernel 根 namespace 传只读零 mask 对象，user 始终传真实 per-MM 页，删除 core 中重复的指针 NULL 判断。改动小、代码减少、`setns()` 语义不变。
2. **专用化 RAW/BOOTTIME/TAI core**：沿用 realtime/monotonic 已验证有效的模式，让 user entry 直接 tail-jump 到常量 base/cycles 的共享 core，避免 `other` 中运行时选择多个指针。PMU 显示这些路径当前多 22–30 条指令、5–9 个分支，是最有依据的热点优化。
3. **拆开 realtime coarse 与 monotonic coarse**：让 monotonic coarse 直接读取固定 base 并做一次 mask 检查，删除 index、`index &&` 和依赖链。当前 monotonic coarse 多 4 个分支且稳定偏慢。
4. **把明确不支持的 ID 在 user entry 冷分支直接送入 syscall stub**：raw 也在 wrapper 层完成 native fallback。该改动可绕过 shared `other/core` 和 `fallback_mode`，目标是回收已测得的 14–18 cycles；必须保证 supported-clock 快路径的比较数不增加。
5. **把 non-NULL context 设为内部 ABI 前提**：删除 `vkso_fallback()` 的 `!context` 防御检查；`fallback_mode` 仍需保留，以区分 kernel 返回和 user syscall。
6. **保持现有 seq 和 shared cache-line 布局**：它们已经给出低 retry，且没有 cache miss 是瓶颈的证据。

暂不建议：

- 在 wrapper 初始化时把根 namespace 永久绑定为 NULL，因为会破坏随后发生的 `setns()`；
- 删除 seq、放宽一致性，或故意延长 odd 窗口；
- 为 fallback 把 syscall 代码 inline 到每个 shared core，代码增长明显且只改善冷路径；
- 继续调整 return thunk、retpoline 或 cache-line 布局，本轮证据不支持它们是主要矛盾；
- 优先改 `clock_getres`、time、getcpu 等 15–25 cycles 的极短接口，它们更容易受代码对齐影响，当前也没有稳定的共同瓶颈。

每次优化都应满足：

- 功能矩阵不变；
- normal 配置优先，不用关闭安全机制换性能；
- 目标接口的 retired instructions/branches 确实下降；
- 全量 20 接口至少重复一轮，防止拆东墙补西墙。



## 13. 实验的有效边界

本报告可以支持的结论：

- 本机、本内核版本、本编译器和本轮控制条件下，VKSO 与 raw vDSO 的完整 reader 性能差异；
- fallback、直接 syscall 和 seq 协议的相对表现；
- 额外指令与分支是 reader 差距的主要直接原因；
- thunk 不是主要原因。

本报告不能单独支持的结论：

- update-side 一定更快或更慢；它需要独立的 update benchmark；
- 所有 CPU 微架构上的绝对 cycles 都相同；
- 一次启动中 1% 左右的 syscall 差异一定来自 VKSO 设计；
- PVClock/Hyper-V 后端性能；本轮裸机使用 TSC。

由于 reader 差异只有几个 cycles，若用于论文最终置信区间，建议再完成至少两轮完整四镜像实验，并把“启动”作为独立样本进行跨启动统计，而不是把同一次启动内的 31 次重复当作 31 次独立系统样本。

作为本轮内部稳定性参考，四组 user 数据按接口计算的 IQR 中位数分别约为 `0.87`、`0.86`、`0.94` 和 `0.96` cycles。单次启动内的数据较集中，但它不能替代跨启动重复。

## 15. 最终判断

本轮实验已经证明：

1. 在所覆盖的 time/getcpu ABI 上，VKSO 功能与 raw vDSO 一致；
2. VKSO reader 已接近 raw，默认配置整体仅慢约 2.37%，快路径的典型绝对差距不到 1 cycle；
3. VKSO 的 seq 重试显著更少，但低冲突率决定了它不是 reader 延迟的主要矛盾；
4. 当前主要性能差距是入口、显式上下文依赖和 other/fallback 路径中的固定指令与分支；
5. 关闭 thunk 不能解决主要差距；
6. VKSO 的 realtime/monotonic 专用路径已经能够持平或超过 raw，说明继续做定向优化是可行的；
7. 论文中应同时报告绝对 cycles、百分比、退休指令/分支和跨启动重复，不能只展示百分比。

因此，当前版本可以作为“功能完整、性能接近原生 vDSO”的 reader baseline。若继续投入优化，目标应是把根 namespace 和 other-clock 的固定上下文成本压缩掉；若不继续优化，本轮数据也足以诚实地说明 VKSO 用很小的 reader 开销换取了内核/用户共享 core code 和更低的 seq 冲突。
