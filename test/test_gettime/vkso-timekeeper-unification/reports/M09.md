# M09 阶段报告：完整正确性验证

## 1. 阶段结论

M09 已完成。重构后的 timekeeper、shared ABI v11、普通 kernel reader、
syscall dispatcher、用户 `__vkso_*` wrapper 和必要 cold backend 在 QEMU 中
通过完整 Raw/VKSO 对照。

本阶段只增加验证能力，不改变生产算法：

- validation 配置启用 `CONFIG_VKSO_TIME_TEST`；
- production 配置明确关闭测试 hook；
- dynamic/PTP 使用外部测试 module，不向产品 backend 加测试分支；
- alarm 无 RTC 使用独立启动真实构造；
- production 产品功能 SLOC 净变化为 0。

M01～M09 的功能重构由此冻结。M10 尚未开始，QEMU 输出中的 cycles 不作
真实性能结论。

## 2. 验证结构

### 2.1 内核上下文 selftest

validation image 定向覆盖：

- early init 中调用普通 `ktime_get_ts64()`；
- local IRQ disabled 下连续读取普通/fast clock；
- local NMI IPI 中读取 mono/raw/boot/realtime fast clock；
- 持有 `timekeeper_lock` 且 `tk_core.seq` 为奇数时调用 writer-safe/private
  reader，证明不会等待自身；
- finite-mask wrap、TSC backward clamp、invalid clock mode；
- 人为改变 seq generation 后必须 retry。

NMI handler 在发布 `seen` 前执行 `smp_wmb()`，等待侧配对 `smp_rmb()`，测试
结果本身不依赖未定义的数据竞争。

### 2.2 public ABI 与路径

`abi_matrix.c` 同时作为 Raw vDSO 和 VKSO direct ABI 客户端，覆盖：

- 七种 global clock、`clock_getres`、`gettimeofday`、`time`、`getcpu`；
- process/thread CPU 固定 ID 与 encoded ID；
- realtime/boottime alarm；
- dynamic/FD clock 成功、无效 FD 和 invalid ID；
- NULL、非法输出地址、errno 保持和返回 ABI；
- root/non-root namespace、fork、exec、setns、多线程、多 CPU；
- seccomp 路径判定与 ptrace fallback syscall 次数；
- text R-X、shared/context R--/NX。

合法 dynamic clock 由 `vkso_m09_clock.ko` 注册 `struct posix_clock`，避免只测
无效 FD 冷路径。process CPU gettime/getres 与 dynamic gettime 各自只观察到
一次目标 syscall 的 entry/exit pair，没有 fallback 重入。

### 2.3 真实 producer/event 路径

测试实际触发：

- `clock_settime`；
- `ADJ_TAI`；
- `ADJ_FREQUENCY`；
- UTC 日界处的真实 leap insertion，并观察 TAI-realtime offset 增加一秒；
- TSC→HPET→TSC clocksource switch；
- HPET 下的 user provider fallback；
- QEMU S3 suspend/resume 与 RTC wakeup；
- VKSO page replace、执行和 restore 生命周期。

clocksource 不受 user provider 支持时：

- `clock_gettime(CLOCK_REALTIME)` 与 `gettimeofday` fallback；
- `clock_getres(CLOCK_REALTIME)` 与 `time()` 保持 fast；
- 切回 TSC 后 shared provider 恢复。

### 2.4 alarm 有/无 RTC

正常启动验证 alarm gettime/getres 成功。另为 Raw/VKSO 各启动一次
`initcall_blacklist=cmos_init,add_rtc_cmos` 内核，从启动时形成无 RTC
alarm backend，验证两个 alarm clock 的 gettime/getres 共四项均返回
`-EINVAL`。

没有修改 `alarmtimer.c` 或伪造其内部 `rtcdev`；测试走的是 Raw 与 VKSO 都会
使用的真实 cold backend。

## 4. seq 并发证据

production QEMU 中每个 reader 执行 500,000 次：

| backend | reader | completed | retries |
|---|---|---:|---:|
| Raw | hres protocol | 500,000 | 0 |
| Raw | raw protocol | 500,000 | 0 |
| VKSO | hres protocol | 500,000 | 0 |
| VKSO | raw protocol | 500,000 | 0 |

这证明测试期间无 seq 死循环、未完成读取或协议异常。零 retry 只表示本次
QEMU 调度窗口没有碰撞，不代表裸机 retry 概率或性能结论；M10 仍需真实并发
测量。

## 7. 代码规模与结构结论

相对 M08，本阶段内核源码变化只有 CONFIG 控制的 T1 selftest：

- header 声明 3 行；
- writer-held test 20 行；
- test translation unit 净增 92 行；
- dynamic module 95 行 C + 13 行 Makefile；
- 其余变化是 ABI matrix 和构建/QEMU orchestration。

这些内容不进入 production image 的读取、更新、dispatcher 或 backend 热/冷
路径。M09 没有重新引入：

- global 算法复制；
- compat conversion；
- fallback mode；
- v10/v11 双路径；
- alarm/CPU/dynamic 产品测试分支。

因此 `CODE_SIZE_MANIFEST.md` 的产品边界保持不变，`X1=0`。最终 Raw/VKSO
产品 SLOC 和 symbol bytes 仍按 M10 的人工语义分类复算，不能把本阶段测试
规模计入 VKSO 功能工作量。
